# DOUBLEBLIND

**Adversarial evaluation is a protocol between mutually distrusting parties, not an environment they share.** DOUBLEBLIND puts a red team, a blue team and the model under test in separate trust domains and mediates every permitted message through a single gateway that tags, scans, reduces, pads and logs it, so the output of a run is not a finding but a finding *plus machine-checkable evidence about the conditions it was produced under*: per-session canary markers that name the source session of any cross-session leak rather than merely counting it, a SHA-256 hash-chained audit log whose edits are localised to an index, fixed-tick release that cuts a latency side channel from a distinguishing advantage of 1.000 to 0.502 at a measured cost of +196 ms, Shadow Replay re-running a finding in independently opened sessions to report a reproduction rate with a Wilson interval instead of a boolean, and a two-arm controlled experiment with a negative control showing that a one-turn probe of a deliberately misconfigured deployment comes back clean 87% of the time while the same deployment probed for three turns never does — which is why a harness that tests in single turns is sampling the condition under which contamination is least visible. Python 3.12, standard library only, no dependencies and no credentials: `py -3.12 scripts/demo.py` runs seven acts in about twenty seconds, `py -3.12 -m doubleblind.api` serves the dashboard at <http://127.0.0.1:8800>, `py -3.12 -m unittest discover -s tests` runs 55 tests aimed at the controls rather than the happy path, and [docs/THREAT_MODEL.md](docs/THREAT_MODEL.md) states what this does *not* protect — a shared kernel, one trusted gateway, microarchitectural channels, and contamination that carries no marker.
